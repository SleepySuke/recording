# 录音转写服务开发计划（Go + MySQL，12～16 小时）

状态：MySQL 修订稿。对应设计见 [总体架构](../design/architecture.md) 与 [详细技术设计](../design/technical-design.md)（含存储选型对比、DDD 分层、事件日志与错误码）；测试用例见 [测试设计](../design/test-design.md)。以 14 小时为基线，最多 2 小时缓冲；收到题目后 7 个自然日内提交。README 已有设计初稿，交付阶段更新为实际验证结果。

## 2. 时间预算约束

若实际只有 12 小时：保留全部 P0、DDD 分层、数字码与事件表；将处理中任务的自动重排简化为 failed + 30003，并写 task_interrupted 事件供手动重试；减少可选抽象与文档润色。12 小时为紧缩方案，不能默认保证与 14 小时方案同等加分范围。

14 小时基线包含事件表、提交后 slog 事件镜像和简单从头恢复（事件导出器已从方案中移除，事件提交后直接镜像到 logs/app.jsonl）。剩余缓冲优先修复测试、容器启动、真实 LLM 输出等问题，不默认添加新功能。

如果进度提前，按实际剩余时间选择一个小项；不同时叠加自动重试、SSE、上传幂等和公网部署。上传幂等实现成本最低（content_hash 已随表结构预留，仅需实现命中复用逻辑），可优先选择。自动重试会引入执行次数、退避时间、手动重试交互等新语义，应在 P0 验收通过后另做决策。

## 3. 验收清单

### 上传与查询

- 四种扩展名可上传，返回 202 与 pending，不等待转写和摘要；元数据与任务成对落库。
- 缺 file、不支持扩展名、空文件返回 400；超 50 MiB 返回 413，且没有残留任务和文件。
- 测试恰好大小上限和超限 1 字节，确认 multipart 开销不会被误当成音频大小。
- 文件名净化与扩展名解析边界（双后缀、无后缀、控制字符、超长名、多余 file 部分取第一个）有测试覆盖。
- 不存在资源返回 404；分页缺省、非法值、上限、空列表、倒序行为正确。
- 同时校验 HTTP 状态与业务错误码，验证 405/Allow、未知路由和 204 空响应；模拟网络失败时不假设必有 JSON 业务码。
- 任务查询明确体现 transcribing 和 summarizing；done 详情含 transcript 和三个摘要字段。

### 异步与真实摘要

- 生产 Mock 行为符合 5～15 秒随机耗时与约 20% 失败概率；自动化测试不依赖抽样碰运气。
- worker 并发不超过配置；多个 worker 不会同时认领同一执行轮次。
- 使用隔离 MySQL 测试库验证行锁、SKIP LOCKED、统一锁顺序、逻辑关联事务与 JSON；测试不得连接业务数据库。
- 验证数字码类型和唯一性、Gin 统一错误、channel 满时不阻塞、context 取消/退出和 WaitGroup 回收。
- 覆盖三表删除回滚、关联巡检、task_id 跨轮次事件链与事件插入失败回滚。
- 覆盖提交结果未知时保留文件与核对记录，避免网络错误后误删已提交录音。
- 确定性转写失败会进入 failed 并记录原因。
- 真实 LLM 调用产生可验证结果；模拟超时、非 2xx、坏 JSON、缺字段、类型错误均可进入 failed。
- 日志可按 task_id 和 event_seq 还原跨 attempt 的完整生命周期，不包含密钥或完整音频/转写内容。

### 重试、删除与恢复

- 仅 failed 可重试；并发重复请求只有一次成功状态更新，其他返回 409，不新增任务。
- 旧 attempt 无法覆盖新 attempt 的状态和产物。
- pending、transcribing、summarizing、done、failed 均可删除，最终文件与关联数据消失。
- 删除中的 worker 无法回写结果；文件暂时删除失败可重试清理。
- 重启后 pending 可被认领；基线方案中的在途任务从头执行；done/failed 不被意外重跑。
- 启动恢复在途删除及孤立文件清理，不误删仍被数据库引用的文件。

### 交付

- 新环境 `make setup` 配置真实 LLM 后，`make start` 一条命令启动至就绪（自动环境检查；镜像已存在直接复用，缺失才构建/拉取）；不需要额外手动建表。`make check` 可单独自检，`make dev` 本地免镜像运行，`make test` 全量（含 E2E）、`make e2e` 单独端到端、`make lint` 均可用。
- 验证 logs 宿主机挂载、文件可写与轮转。
- Compose 包含 app 与 db，验证数据库就绪、迁移失败时应用不就绪，以及两个数据卷的持久化。
- 重建容器后录音文件与 MySQL 数据仍存在。
- `go test ./...` 通过；并发状态相关测试在环境支持时执行 race 检查。
- 调试文件覆盖全部六个核心接口，包含替换 ID 和查看失败重试的说明。
- README 明确单实例、重试语义、重启重做可能重复调用 LLM、已知问题及未完成项。
- README 的功能状态和命令均按实际验收更新，移除仅设计阶段的说明；架构、数据流、ER 与状态图保持和代码一致。
- 仓库没有 API Key、真实用户录音、数据库文件或构建产物；Git 历史体现持续开发。

## 4. 建议演示顺序

启动服务并展示自动迁移 → 上传录音 → 查询 pending/当前阶段 → 查看成功摘要 → 演示失败及手动重试 → 展示分页列表 → 删除并确认文件和数据清理 → 演示在途任务重启恢复 → 运行核心测试。

演示失败用明确标识的开发/测试注入方式或测试用例，避免等待随机失败；不能把测试替身当作真实 LLM 验收结果。真实 LLM 成功演示保留脱敏的命令与响应，便于复现。

## 6. 首轮之后的扩展顺序

以下不计入本次 12～16 小时承诺，需独立估时。

1. 如需分享体验，先部署已验收 API；没有前端也可通过调试文件使用，公网部署不是首轮前置条件。
2. 增加最小前端：上传、列表、状态轮询、详情、重试与删除；同源托管可减少跨域配置，前端不接触 LLM/ASR 密钥。
3. 接入真实 ASR：实现 Transcriber 适配器，读取真实音频，处理供应商格式限制、超时、失败；异步供应商还需处理轮询/回调，不能假设只是替换一个 URL。
4. 根据真实使用问题选择上传幂等、跨轮次 retry 幂等、自动重试或 SSE；多实例之前先解决文件共享和任务租约。

前端与真实 ASR 可以按演示目的调整顺序：展示交互先做界面，验证真实音频内容先做 ASR。题目允许 Mock ASR，真实 LLM 仍是首轮要求。
